## ROOT CAUSE FOUND (device log): play() during BUFFERING freezes the playhead

- User reported the scrub-then-play lag still present. Pulled the app log again:
  every `play()` issued at `playbackState=2 (BUFFERING)` froze the playhead —
  it only ever advanced via the stall-recovery nudges (33 ms every ~500 ms,
  i.e. the "lag korte korte" stutter) — while every `play()` at `state=3
  (READY)` played perfectly (three clean sessions in the log). After 10
  nudges the old loop just gave up, leaving a frozen "playing" UI.
- Fix: playback is now two-phase in `EditorViewModel.startPlaybackPolling()`:
  Phase 1 waits for `STATE_READY` at the playhead and only then calls
  `manager.play()` (`PlayerRecoveryPolicy.shouldDeferPlay` documents why);
  if READY never arrives within `WAIT_READY_TICKS` (3 s) the composition is
  rebuilt at the playhead (`MAX_READY_REBUILDS = 2`). A broken (IDLE+error)
  player rebuilds immediately. Phase 2 keeps the #3452 stall detection, but a
  freeze episode gets 2 nudges, then a forced rebuild, then gives up; the
  recovery budget resets once the playhead advances >1 s past the last
  recovery point.
- `PlayerRecoveryPolicy`: added `WAIT_READY_TICKS = 60`, `shouldDeferPlay()`;
  `PlayerRecoveryPolicyTest`: added the defer test.
- Verified: 386 tests, 0 failures; APK rebuilt and installed via adb
  (`Success`). Expected UX: a short buffering pause (~100-300 ms) after
  scrubbing, then smooth playback.

- 17:40 session log: `play(): deferred until the player is ready (state=2)`
  and the player NEVER became READY — user paused after 1-2.5 s each time.
  Earlier 13:58 session: even two full `loadProject(forceRebuild)`s at the

- Conclusion: CompositionPlayer 1.11.1 cannot recover from a >~100 ms seek —
  and `setComposition()` on a SAME instance never recovers it either. The old
  one-frame nudges were fake progress: `seekTo()` writes the target into the
  position flow synchronously, so the watchdog "advanced" without a single
  frame rendering.
- Fix (rebuild-fresh strategy):
  - `PlayerManager.loadProject(forceRebuild = true)` now ALWAYS releases and
    recreates the CompositionPlayer (fresh instance + setComposition + prepare
    is the only path proven to reach READY).
  - New `PlayerManager.rebuildPreviewAt(positionMs)` = pause + safeStart snap
    + forced fresh rebuild; replaces `recoverStalledPlayback()` (deleted) and
    `PlaybackStartPolicy.recoverySeekMs` (deleted + tests removed).
  - `EditorViewModel`: `scrubbedSincePlay` flag set by every `seekTo()`;
    `startPlayback()` rebuilds fresh at the playhead when it was scrubbed
    (including restart-from-end), else keeps the cheap resume path. Phase 2
    stall recovery now rebuilds directly (no nudges), budget MAX_READY_REBUILDS.

## Root cause of the resume bug: Media3 CompositionPlayer 1.11.1 defects

- The resume freeze was not an app state-machine bug. Two upstream defects
  (androidx/media issues, Media3 1.11.1) explain the repro exactly:
  - **#3452**: playback that *starts* on the last frame of an outgoing sequence
    item advances ~100-150 ms then freezes for good (playWhenReady stays true).
    Tested workaround: start on the item boundary (0/316 probes froze).
  - **#3482**: seeking to the position the player already reports while paused
    flushes the audio graph; the following play() starts silent.
  - The fixed-centre timeline makes #3452 easy to hit: scrolling while paused
    parks the playhead on a clip's final frame. `startPlayback()` also re-seeked
    to the position a scrub had already applied (#3482).
- `PlaybackStartPolicy.kt` (NEW, pure + tested): `GUARD_FRAMES=2`,
  `frameDurationMs`, `mainClipBoundariesMs`, `safeStartMs` (boundary nudge,
  end-of-timeline restart to 0) and `recoverySeekMs` (one-frame nudge).
- `PlayerManager.kt`: `play()` now moves a paused start off a clip's last frame;
  `seekTo()` skips same-position seeks while paused; added
  `safeStartPositionMs(positionMs)` and `recoverStalledPlayback()` (nudge +
  play; the nudge is itself normalised through the safe-start policy because a
  frozen player can still report isPlaying=true).
- `EditorViewModel.kt`: `startPlayback()` no longer re-seeks to the position a
  scrub applied — it only syncs when the two position flows genuinely diverged
  (project switch); `startPlaybackPolling()` stall detection is now
  position-based (no `isPlaying` input, since #3452 keeps it true) and calls
  `recoverStalledPlayback()` instead of only re-issuing play().
  `openProject()` loads at start 0 explicitly instead of inheriting the previous
  project's playhead.
- `PlayerRecoveryPolicy.kt`: `shouldRetryPlay` replaced by
  `shouldRecoverStall(startupGraceOver, stalledTicks)`; class doc updated.
- Tests: new `PlaybackStartPolicyTest` (12 cases), `PlayerRecoveryPolicyTest`
  updated to the position-based rule.
- STATUS: shell tool is broken on this machine (pwsh launcher cannot resolve
  `C:\Users\HP 840G5-i7\...` because of the space in the username), so
  `:app:compileDebugKotlin :app:testDebugUnitTest` must be run by the user.

## Second round: the "playhead crawls and sticks in the middle" symptom

User report (after the first round): "timeline ekto agee pore move kore ... play
button click kole laggay vabe timeline move kore majhe modhe stuck hoye thake"
— the playhead advances slowly and freezes in the middle of the timeline.

Four concrete defects were found in the code and fixed:

1. **The start guard was too narrow.** #3452 freezes ~130-150 ms *after* the
   start, i.e. ~100 ms *past* the cut, so a 2-frame (66 ms) guard still allowed
   starts that froze right after a transition. `PlaybackStartPolicy` now uses
   `TRANSITION_WINDOW_MS = 150` (guard = max(2 frames, 150 ms)) and snaps such a
   start onto the cut (the tested-safe position).
2. **The watchdog counted buffering as a freeze.** At a clip cut the incoming
   item loads, CompositionPlayer pauses its internal players
   (`setPlayWhenReadyInternal(false)`) and restores them when every item is READY
   again — the playhead legitimately stops during that window. The stall counter
   fired there and issued nudge-seeks at *every* transition: the playhead crawled
   33 ms per recovery and got stuck. `PlayerRecoveryPolicy.countsAsStallCandidate()`
   now excludes `STATE_BUFFERING`; a player that stays buffering for
   `WAIT_READY_TICKS` (3 s) is rebuilt at the playhead instead.
3. **Every press rebuilt the player.** `play()` used `isBroken(lastError, state)`,
   which is true whenever an error string is stored — and the error string
   survives a successful recovery (the ExoPlayer fallback keeps it set). Each Play
   therefore re-created the media items: a visible lag on every start.
   `PlayerRecoveryPolicy.shouldRebuildBeforePlay()` now rebuilds only when the
   player cannot answer play() (STATE_IDLE) or carries an error in no usable
   state.
4. **`play()` could land while the player was still BUFFERING.** `shouldDeferPlay`
   existed but was never used. `PlayerManager.play()` now checks the LIVE player
   state, defers the play when the player is not READY/ENDED and returns `false`;
   `EditorViewModel`'s Phase-1 loop only marks the play as issued when the play
   was really handed to the player (otherwise the preview would stay silent).

Files touched: `PlaybackStartPolicy.kt`, `PlayerRecoveryPolicy.kt`,
`PlayerManager.kt` (`play()` now returns Boolean), `EditorViewModel.kt`,
`PlaybackStartPolicyTest.kt` (guard-window case rewritten for 150 ms),
`PlayerRecoveryPolicyTest.kt` (+4 cases for the new rules).

## Third round: playback works, but the timeline scroll feels laggy

User report: "Fix hoise but play houar somoi timline smoothly move kore nah laggy
feel hoi" — playback itself is correct, the timeline does not move smoothly.

Two causes, both fixed:

1. **The playhead only updated 20 times per second.** `startPlaybackPolling()`
   polled `PlayerManager.syncPosition()` every 50 ms, so the timeline
   auto-scroll (and the timecode) jumped in visible steps even though the video
   itself was smooth.
2. **Every playhead tick recomposed the whole editor.** `EditorScreen` collected
   `currentPositionMs` with `collectAsState()`, so the ENTIRE screen — video
   canvas, timeline with all tracks, toolbars — was rebuilt on every tick, for a
   value the timeline only uses to drive one scroll sync.

Changes:
- `PlayerRecoveryPolicy`: `TICK_MS`/`WAIT_READY_TICKS` replaced by
  `POSITION_TICK_MS = 16` (~60 Hz playhead refresh), `WATCHDOG_STRIDE = 3`
  (the recovery watchdog keeps its old ~50 ms cadence),
  `WAIT_READY_POSITION_TICKS = 180` (`WAIT_READY_TICKS` semantics preserved) and
  `WAIT_BUFFERING_WATCHDOG_TICKS = 60` — all budgets mean exactly what they
  meant before.
- `EditorViewModel.startPlaybackPolling()`: the playhead syncs every 16 ms; the
  freeze/buffering watchdog runs only every third tick (phase 1 still reacts
  instantly; phase 2 keeps `STALL_TICKS`/`STARTUP_GRACE_TICKS` semantics). The
  buffering recovery additionally uses `rebuildPreviewAt` (the proven path)
  instead of pause+loadProject.
- UI plumbing: the position is now a `State<Long>` that is handed down.
  `EditorScreen` no longer collects the playhead (it mirrors the flow into a
  `MutableState` and passes the State down, never reading it in its body);
  `VideoCanvas` and `CapCutTimelineLeftGutter` read `.value` because they
  genuinely need it; `MultiTrackTimeline` reads it ONLY inside its two
  scroll-sync effects, so the timeline and its tracks never recompose during
  playback.
