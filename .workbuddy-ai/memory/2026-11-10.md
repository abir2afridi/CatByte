  it only ever advanced via the stall-recovery nudges (33 ms every ~500 ms,

  freeze episode gets 2 nudges, then a forced rebuild, then gives up; the
  recovery budget resets once the playhead advances >1 s past the last
  recovery point.

## Root cause of the resume bug: Media3 CompositionPlayer 1.11.1 defects

- The resume freeze was not an app state-machine bug. Two upstream defects
  (androidx/media issues, Media3 1.11.1) explain the repro exactly:
  - **#3452**: playback that *starts* on the last frame of an outgoing sequence
    item advances ~100-150 ms then freezes for good (playWhenReady stays true).
    Tested workaround: start on the item boundary (0/316 probes froze).
  - **#3482**: seeking to the position the player already reports while paused
    flushes the audio graph; the following play() starts silent.
  - The fixed-centre timeline makes #3452 easy to hit: scrolling while paused
    parks the playhead on a clip's final frame. `startPlayback()` also re-seeked
    to the position a scrub had already applied (#3482).
- `PlaybackStartPolicy.kt` (NEW, pure + tested): `GUARD_FRAMES=2`,
  `frameDurationMs`, `mainClipBoundariesMs`, `safeStartMs` (boundary nudge,
  end-of-timeline restart to 0) and `recoverySeekMs` (one-frame nudge).
- `PlayerManager.kt`: `play()` now moves a paused start off a clip's last frame;
  `seekTo()` skips same-position seeks while paused; added
  `safeStartPositionMs(positionMs)` and `recoverStalledPlayback()` (nudge +
  play; the nudge is itself normalised through the safe-start policy because a
  frozen player can still report isPlaying=true).
- `EditorViewModel.kt`: `startPlayback()` no longer re-seeks to the position a
  scrub applied — it only syncs when the two position flows genuinely diverged
  (project switch); `startPlaybackPolling()` stall detection is now
  position-based (no `isPlaying` input, since #3452 keeps it true) and calls
  `recoverStalledPlayback()` instead of only re-issuing play().
  `openProject()` loads at start 0 explicitly instead of inheriting the previous
  project's playhead.
- `PlayerRecoveryPolicy.kt`: `shouldRetryPlay` replaced by
  `shouldRecoverStall(startupGraceOver, stalledTicks)`; class doc updated.

## Second round: the "playhead crawls and sticks in the middle" symptom

User report (after the first round): "timeline ekto agee pore move kore ... play
button click kole laggay vabe timeline move kore majhe modhe stuck hoye thake"
— the playhead advances slowly and freezes in the middle of the timeline.

Four concrete defects were found in the code and fixed:

1. **The start guard was too narrow.** #3452 freezes ~130-150 ms *after* the
   start, i.e. ~100 ms *past* the cut, so a 2-frame (66 ms) guard still allowed
   starts that froze right after a transition. `PlaybackStartPolicy` now uses
   `TRANSITION_WINDOW_MS = 150` (guard = max(2 frames, 150 ms)) and snaps such a
   start onto the cut (the tested-safe position).
2. **The watchdog counted buffering as a freeze.** At a clip cut the incoming
   item loads, CompositionPlayer pauses its internal players
   (`setPlayWhenReadyInternal(false)`) and restores them when every item is READY
   again — the playhead legitimately stops during that window. The stall counter
   fired there and issued nudge-seeks at *every* transition: the playhead crawled
   33 ms per recovery and got stuck. `PlayerRecoveryPolicy.countsAsStallCandidate()`
   now excludes `STATE_BUFFERING`; a player that stays buffering for
   `WAIT_READY_TICKS` (3 s) is rebuilt at the playhead instead.
3. **Every press rebuilt the player.** `play()` used `isBroken(lastError, state)`,
   which is true whenever an error string is stored — and the error string
   survives a successful recovery (the ExoPlayer fallback keeps it set). Each Play
   therefore re-created the media items: a visible lag on every start.
   `PlayerRecoveryPolicy.shouldRebuildBeforePlay()` now rebuilds only when the
   player cannot answer play() (STATE_IDLE) or carries an error in no usable
   state.
4. **`play()` could land while the player was still BUFFERING.** `shouldDeferPlay`
   existed but was never used. `PlayerManager.play()` now checks the LIVE player
   state, defers the play when the player is not READY/ENDED and returns `false`;
   `EditorViewModel`'s Phase-1 loop only marks the play as issued when the play
   was really handed to the player (otherwise the preview would stay silent).

Files touched: `PlaybackStartPolicy.kt`, `PlayerRecoveryPolicy.kt`,
`PlayerManager.kt` (`play()` now returns Boolean), `EditorViewModel.kt`,
`PlaybackStartPolicyTest.kt` (guard-window case rewritten for 150 ms),
`PlayerRecoveryPolicyTest.kt` (+4 cases for the new rules).
STATUS: still unverified on device — the shell tool is broken, so the user has to
run `.\gradlew.bat :app:compileDebugKotlin :app:testDebugUnitTest --console=plain`,
then `:app:assembleDebug` + `adb install -r`, then reproduce

## Fourth round: scrolling the timeline showed a 1-2 s BLACK preview

User report: "timeline scroll korle video preview te 1/2sec black screen hoye
video scene dekhai ... timeline scroll korle realtime video scene dekhai nah
preview te".

ROOT CAUSE (CompositionPlayer 1.11.1): a seek is only settled while the frame
processor is processing frames — `waitingForFrameAfterSeek` is cleared from
`onFrameProcessed()`, and `setPlayWhenReadyInternal()` only calls
`startRendering()` when `playbackState == READY && playWhenReady`. So EVERY seek
issued while the preview is paused parks the player in STATE_BUFFERING: the
preview stays black until a whole new player is built. The previous "fix"
(release the player + rebuild after every scrub) therefore produced exactly the
reported black flash, and no frame ever appeared while the finger moved.

Changes:
- `PlayerManager`: new scrub API — `beginScrub()` keeps the render loop alive
  (muted: scrubbing is a picture operation), `endScrub()` stops it leaving the
  last frame on the surface, `endScrubKeepPlaying()` for a Play press mid-drag,
  and `previewIsReady()` to detect a seek that never settled.
  `rebuildPreviewAt()` is now the LAST RESORT (documented as such).
- `EditorViewModel.seekTo()`: the playhead still follows the finger instantly,
  but the preview follows with a live seek every `SCRUB_SEEK_MS = 80` while the
  player renders — CapCut-style live scrub preview. `SCRUB_SETTLE_MS = 250` of
  silence ends the gesture (new private `settleScrubAt()`); only if the preview
  is still not READY does it fall back to the rebuild.
- `EditorViewModel.pausePlayback()` flushes a pending scrub with the same live
  seek instead of the rebuild, and only then snaps the UI playhead to the frame
  the player actually shows (the old order snapped BEFORE the seek, which moved
  the playhead back).
- `EditorViewModel.startPlayback()`: no more rebuild-after-scrub. It keeps the
  scrub rendering (`endScrubKeepPlaying()`), only re-seeks on a REAL divergence
  (`PLAYHEAD_RESYNC_TOLERANCE_MS = 750`), and `rebuildPreviewAt` is gone from
  this path.
- `PlayerManager.play()`: the safe-start correction now enables rendering before
  seeking, for the same park reason (that seek used to be issued on a paused
  player).
- Renamed `scrubbedSincePlay` -> `scrubSettlePending` (its real meaning now).

STATUS: needs a build on the user's machine. Watch the preview while dragging
the timeline: it should follow the playhead with a short (~1-2 frame) delay and
never go black. The rebuild remains as a safety net, so a device where the live
seek cannot settle degrades to the old (black) behaviour instead of breaking.

## Fifth round: the preview was STILL black during the whole drag

User report: "timeline scroll korle ... scrolling moment e preview screen black
thake" — even with rendering kept alive (round 4), the screen stayed black for
the WHOLE drag and only recovered when scrolling stopped.

ROOT CAUSE (CompositionPlayer 1.11.1): the player renders NOTHING while a seek
is settling. `updatePlaybackState()` puts the composition into BUFFERING as soon
as one internal player buffers and then calls `setPlayWhenReadyInternal(false)`,
which STOPS the render loop until every internal player is READY again. Firing a
seek every 80 ms therefore kept the player permanently in BUFFERING = a
permanently black preview. The round-4 diagnosis ("keep rendering alive") was
necessary but not sufficient: rendering must also not be interrupted by a seek
storm.

Fix: a settle-gated scrub loop (`EditorViewModel.scrubLoop()`), one per gesture:
- the playhead still follows the finger instantly;
- the loop seeks to the LATEST playhead only when the previous seek has landed
  (`previewIsReady()`), polling every `SCRUB_POLL_MS = 24`;
- between seeks the preview shows real video (it plays muted during the drag,
  which is unavoidable with this player version — a seek always blacks the
  surface briefly);
- when the timeline is quiet for `SCRUB_SETTLE_MS`, the loop lands the playhead
  EXACTLY (a final seek + wait for READY), then `endScrub()` pauses on that
  frame and snaps the UI playhead to it;
- if the final seek never lands, `rebuildPreviewAt` remains the last resort.
`pausePlayback()` no longer pauses while the loop is running (that would stop
the render loop and wedge the final seek); the loop's tail does it.
`scrubbedSincePlay` was replaced by `scrubTargetMs` + `scrubLoopActive` +
`scrubSettlePending`. Media3's `setScrubbingModeEnabled` was evaluated and
rejected: it sets PLAYBACK_SUPPRESSION_REASON_SCRUBBING, which makes
`shouldPlayWhenReady()` false and stops the composition render loop entirely.

STATUS: needs a build on the user's machine. Expected: frames visible while
dragging (video chases the needle at the seek-settle rate, brief flickers per
seek are unavoidable), exact frame when the finger lifts, no long black screen.

## Seventh round: scrub preview stopped using the player entirely

User requirement: scrolling the timeline must update the preview frame-by-frame
in realtime no matter how fast the drag, with NO black period at any point.

Conclusion after rounds 4-6: impossible with CompositionPlayer 1.11.1. Every
seek stops the render loop until the seek settles (`updatePlaybackState()` ->
BUFFERING -> `setPlayWhenReadyInternal(false)`), so any player-driven scrub
spends most of the drag black. A paused player keeps its frame, but moving it
requires a seek.

Fix: do not touch the player while dragging. Decode the frame under the needle
straight from the source media and draw it over the preview:
- `ScrubFrameResolver.kt` (new, pure, unit-tested): timeline ms -> source clip +
  source time, honouring cumulative main-track durations, trim and speed
  (`ClipTiming.sourceOffsetForOutputMs`), overlay fallback, top-most overlay.
- `ScrubFrameLoader.kt` (new): one `MediaMetadataRetriever` per source URI
  (LRU, max 3, released on evict), `getScaledFrameAtTime(OPTION_CLOSEST, 720,
  720)` on API 27+ (decodes straight at size, aspect preserved), `getFrameAtTime`
  + manual scale on API 24-26; plain file paths and content URIs both work.
- `EditorViewModel.seekTo()` while paused only moves the playhead and requests a
  frame; requests run on one dedicated decoder thread and the previous request
  is cancelled first, so a fling can never queue decoders. Resolution also runs
  on that thread because a velocity-curve clip integrates the curve.
- A 180 ms quiet timer (`SCRUB_SETTLE_MS`) then lands the real player:
  `beginScrub()` (render on, muted) -> seek -> wait READY near the target
  (`SCRUB_LAND_TIMEOUT_MS = 900`, tolerance 120) -> `endScrub()` -> hold the
  overlay another 120 ms (`SCRUB_FRAME_HANDOFF_MS`) so the black seek window is
  never visible -> clear. Rebuild stays the last resort for a seek that never
  settles.
- Play during/after a scrub: the player is seeked to the VISIBLE playhead with
  the render loop alive (`beginScrub` + `endScrubKeepPlaying`); the overlay is
  held until playback is READY and has advanced >= 32 ms, then cleared.
- `VideoCanvas` draws the bitmap with `ContentScale.Fit` over the surface and
  draws text overlays on top (the extracted frame is raw).
- `PlayerManager.cancelScrub()` (new): project switch/destroy abandons a scrub
  without landing a frame and drops the muted render intent.

Tests: `ScrubFrameResolverTest` (6 cases: cumulative mapping, trim+speed,
exact-end hold, placeholders, overlay fallback, top-most overlay). Full suite
394 tests, 0 failures; `:app:assembleDebug` OK; APK rebuilt.

STATUS: needs device verification. Expected: continuous real frames while
dragging at decode rate (~10-20 fps for 720p sources), no black period, exact
frame on release, smooth play after a scrub.

## Eighth round: scrub latency and timeline jank

User feedback: scrolling still felt late (the scene took a moment to appear)
and the timeline itself felt slightly laggy.

Diagnosis:
- `seekTo()` ran on every scroll event and (a) allocated + cancelled a frame
  decode coroutine and (b) allocated + cancelled a settle-timer coroutine. At
  fling rates that is hundreds of main-thread allocations per second.
- `seekTo()` also recomputed `VideoProject.totalDurationMs` on every event. That
  property walks every track and allocates lists (`flatMap`/`maxOfOrNull`), so
  each scroll pixel did an O(project) pass on the UI thread.
- Exact scrub frames use `getScaledFrameAtTime(OPTION_CLOSEST)`, which decodes
  forward from the previous keyframe. On a long GOP or a 4K source that costs
  100-300 ms, so a latest-wins worker could never catch the finger and the
  preview kept showing scenes that were already stale.

Fix:
- `EditorViewModel` now owns one `Channel<ScrubFrameRequest>(CONFLATED)` and a
  single decode worker. A scroll event only does `trySend`; intermediate

## Ninth round: no player work at all during a scrub

User feedback: still not fixed — the scene did not follow timeline scrolling fast
enough and the preview showed an error ("preview error dekhai preview te").

Diagnosis: the eighth-round settle path still called `beginScrub()` +
`seekTo()` + `endScrub()` on the paused CompositionPlayer, and rebuilt it when
the seek did not settle. That is the exact operation that wedges Media3 1.11.1
and raises the preview error; the adaptive exact/keyframe choice also still ran
expensive exact decodes at the start of every drag.

Fix:
- The scrub path no longer touches the player at all. No `beginScrub`,
  `seekTo`, `endScrub` or `rebuildPreviewAt` while the timeline is scrubbed.
  The preview is driven purely by `MediaMetadataRetriever` frames.
- Drag frames are ALWAYS `OPTION_PREVIOUS_SYNC` keyframes at 480 px
  (`DEFAULT_DRAG_MAX_DIMENSION_PX`); no adaptive exact-first decode. The exact
  `OPTION_CLOSEST` frame (720 px) is decoded only after `SCRUB_SETTLE_MS` of
  quiet, on its own lane.
- Two independent decode lanes/executors: `catbyte-scrub-frame` (conflated
  drag requests) and `catbyte-scrub-exact` (conflated settle request, loader
  capped at 1 retriever). A slow exact decode can never block a resumed drag.
- Removed `scrubUseKeyframes`, `landPreviewAt`, `awaitPreviewAt`,
  `SCRUB_EXACT_DECODE_BUDGET_MS`, `SCRUB_LAND_TIMEOUT_MS`,
  `SCRUB_LAND_TOLERANCE_MS`.
- `scrubSettlePending` stays true after the exact still until Play. On Play,
  `startPlayback()` rebuilds a FRESH CompositionPlayer at the visible playhead
  (`rebuildPreviewAt`, behind the still); fallback uses
  `beginScrub`+`seekTo`+`endScrubKeepPlaying`.
- `ScrubPreviewFrame(bitmap, positionMs)`: the still carries its timeline
  position, so the canvas uses it as the source of truth while scrubbing and
  does not read the live playhead on every scroll tick.
- The scrub overlay is now drawn outside the `player != null` branch, so it
  still appears when the player failed; the `Preview error:` pill is hidden
  while a decoded still is visible. `PlayerManager` clears `_lastError` on
  READY, on a successful fallback load, and via `clearPreviewError()` at
  gesture start.
- `pausePlayback()` only adopts the player position when playback was actually
  running; pressing the timeline while paused starts a new gesture
  (`beginScrubFrameGesture`: generation++, drain both channels, clear error)
  without snapping the visible playhead back.
- Edit-refresh corner case: if `PreviewRefreshScheduler` fires while a scrub
  still is visible, the refreshed project is loaded with `forceRebuild = true`
  at the visible playhead (never a paused seek), and a watcher removes the
  still only once that fresh player is READY and the timeline is quiet. On
  timeout the still stays up (no black, no error pill); Play then rebuilds.
